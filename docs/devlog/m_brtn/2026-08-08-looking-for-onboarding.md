## Контекст

Первоначальный онбординг собирал имя, пол и дату рождения, но не спрашивал,
кого пользователь хочет видеть в приложении. Для дейтинг-сценария это
предпочтение нужно получить до создания профиля и сохранить как часть
пользовательских данных.

## Что сделано

### 1. Добавлен четвёртый шаг онбординга

- Между выбором собственного пола и датой рождения появился вопрос «Who are you
  looking for?».
- Доступны три варианта: мужчины, женщины и отсутствие предпочтения.
- Значением по умолчанию выбрано отсутствие предпочтения, чтобы онбординг не
  вводил скрытое ограничение.
- Прогресс, счётчик оставшихся шагов и финальная кнопка обновлены для четырёх
  экранов.
- Повторяющаяся разметка вариантов выбора вынесена в локальный
  `ChoiceRadioGroup`.

### 2. Расширен мобильный API-контракт

- Добавлен тип `LookingFor` со значениями `male`, `female` и `everyone`.
- Поле `lookingFor` включено в пользовательскую модель и запрос создания
  профиля.
- `App.tsx` передаёт новое значение из онбординга в API вместе с остальными
  данными пользователя.

### 3. Обновлены API и база данных

- Fastify-схема `POST /users` теперь требует и валидирует `lookingFor`.
- Значение сохраняется при создании пользователя и возвращается из `POST
  /users` и `GET /me`.
- В Drizzle добавлен enum `looking_for` и одноимённая обязательная колонка.
- Сгенерирована миграция `0001_premium_arachne.sql`.
- Для существующих строк и обратной совместимости миграции используется default
  `everyone`.

### 4. Добавлена локализация

- Заголовок, пояснение и все три варианта вынесены в semantic i18n-ключи
  `onboarding.lookingFor.*`.
- В пользовательском интерфейсе значение `everyone` отображается как `No
  preference`, точнее передавая смысл «неважно».

## Архитектурные решения

- **Предпочтение хранится в профиле, а не только локально.** Оно должно
  восстанавливаться вместе с сессией и в дальнейшем использоваться серверной
  выборкой кандидатов.
- **Отдельный enum не переиспользует расширенный enum пола.** В текущем
  продуктовом требовании поиск ограничен мужчинами, женщинами или всеми, поэтому
  допустимые значения отличаются от самоидентификации пользователя.
- **Фильтрация карточек пока не добавлена.** Текущий swiper работает на
  локальных демонстрационных профилях; применение `lookingFor` относится к
  будущему серверному подбору кандидатов.

## Риски и открытые вопросы

- Нужно определить, учитывает ли будущий подбор только предпочтение текущего
  пользователя или требует взаимного совпадения предпочтений двух профилей.
- Список вариантов поиска может потребовать расширения после уточнения
  продуктовой модели гендера.
- После запуска API необходимо проверить миграцию на существующей локальной базе
  и пройти обновлённый онбординг на iOS или Android.
